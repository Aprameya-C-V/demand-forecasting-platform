Demand Forecasting Service

An end to end forecasting system for NYC taxi demand: scheduled retraining, a champion/challenger gate before anything reaches production, a served forecast API, and monitoring that opens an issue when the model decays. Every stage runs in CI.

How it runs

  1. IngestMonthly TLC parquet, checksummed and recorded in a manifest.
  2. ValidatePanel contract: dense zone-slot grid, no nulls, no negative counts. Fails the pipeline on a gap.
  3. TrainTime based split, LightGBM point model plus p10 and p90 quantile models, early stopping on a validation window.
  4. GateRegistered version replaces production only if WAPE improves by at least 2%. Otherwise it is kept as a challenger.
  5. ServeFastAPI: health, readiness, model metadata, zone forecasts, Prometheus metrics, every request logged.
  6. MonitorReplays realised demand, computes WAPE, bias and PSI per feature, then opens a GitHub issue when a gate breaks.

What makes it a platform

Promotion is a gate, not a habitA challenger is registered on every training run but replaces production only when it beats the champion by the configured margin. The alias, not the code, decides what serves.
Monitoring has teethThe scheduled workflow fails on a WAPE, bias or PSI breach and opens a GitHub issue with the numbers, so a regression is a tracked ticket rather than a dashboard nobody reads.
Contracts before modelsThe panel is validated before training: wrong zone count, duplicate rows or a missing slot stops the run. A silent gap in the panel would corrupt every lag.
One code path for train and serveFeature engineering reshapes the dense panel into a cube, so the served lag is computed by the same function that trained it.

Reproduce

uv venv && uv sync
uv run forecast fetch          # download the published TLC months
uv run forecast panel          # aggregate and validate to data/processed/panel.parquet
uv run forecast train          # train, register, promote if the gate passes
uv run forecast monitor        # replay realised demand, write reports and dashboard data
uv run forecast serve          # http://127.0.0.1:8000/docs

Limits

One run per configuration, so only large differences are claimed. Synthetic-free but aggregate-only data: no weather, events or road closures, which is the obvious next feature source. The panel ends at the last published month, so the API forecasts one day ahead rather than recursively for a week. Cost of serving is not measured.
